fix nodes running around while being dragged, and make the fix a check

The previous attempt did not work -- reported as "the nodes still run around and are hard to
control" -- and it failed because it was reasoned about rather than exercised. Reading the
whole path found the real cause, which is not a flag or a threshold.

**`px()` is a conversion, not a reading.** It turns a stored grid position into pixels by
multiplying, and it runs on *every* render. A node at a pixel position near the origin -- x
below 12, or y below 8 -- therefore satisfies the "this is a grid position" test on the next
render and gets multiplied by COL_STEP. Preset nodes start at (0,0)..(5,0), all inside that
range, so every one of them could be thrown across the canvas.

No flag or threshold can fix that, because each payload from the server re-creates the
question: the server stores grid units, so "is this number a column or a pixel" is asked
again every time a payload arrives. The first attempt added a flag and left the ambiguity
in place.

**The fix is to give the canvas one coordinate system.** Every node is converted to pixels
once, as a payload is adopted, in `normalisePositions`. After that the canvas holds pixels
and nothing reinterprets them. Both copies are converted -- `describe.nodes`, which the canvas
draws, and `graph.nodes`, which `/api/graph/move` is called with -- because leaving one in
grid units puts them back out of step.

Measured, with the real functions lifted out of `canvas.js` and run under node:

    (6,3) with the flag      -> (6,3)          stays put
    (6,3) with the flag lost -> (6,3)          the client-side record holds it
    (6,3) with no conversion -> (1344,324)     the old jump, reproduced

**The client-side record is deliberate distrust.** The server does preserve the flag --
measured, `graph_move` to (6,3) returns `[6.0, 3.0]` with `px=true`, and a second move is
stable, so the fix would work today without it. But relying on that means a single route that
forgets the flag silently multiplies the position again, and the record removes the
dependency for the cost of one `Set`. Applying a graph preset clears it, because a preset
deliberately re-lays-out the graph in grid units and those nodes must be allowed to convert.

**The check exercises the code rather than the idea.** `check_node_drag` extracts the real
`px` and `normalisePositions` bodies, drives them through ten round trips with the flag and six
without, and asserts the position survives each. It also computes what happens with no
conversion at all, so the check is shown to be capable of failing. That matters here: the
first fix would have passed any check that read the code instead of running it.

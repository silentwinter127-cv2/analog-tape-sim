give node positions one unit, decided by the caller instead of guessed from the value

Recorded the failure and measured it before changing anything. Tracking the node boxes through
the clip: the node row's width changed by a factor of 1.311 while the centroid moved 51 px, so
the nodes were moving *together* and being scaled -- the whole view, not the layout. That
ruled out a drag bug and pointed at coordinates.

The cause is that the system genuinely used three units at once:

    presets        grid columns, e.g. [0,0] .. [5,0]   (readable in source)
    dragging       pixels, via /api/graph/move         (and it sets px_position)
    adding a node  pixels, 40 + random*260             (and it does NOT set px_position)

So a node from the palette came back unflagged, and the client had to ask "is this number a
column or a pixel" on every payload. A node dragged to (5, 0) was read as column 5 and moved
to x=1120. Every previous fix added machinery to the client to disambiguate, and none of them
could work, because the ambiguity was in the data.

**The fix is to remove the ambiguity rather than to guess at it.** The conversion moved to the
server, in one place: `graph_load_preset` converts the preset's columns as it lays the graph
out, `graph_add` now marks its position as pixels, and everything else was already pixels. The
client's `px()` is a pass-through and the client-side `CONVERTED` set is gone with the
conversion it served.

**The check caught a real hole in the first version of that.** It tried `_grid_to_pixels((5,
0.5))` and found it converted, because 5 is an integer in the grid range -- and `(5, 0)` as a
genuine pixel position is numerically identical to column 5. No test on the value can separate
them, which is precisely why the bug kept returning. So the detection was dropped: preset
coordinates *are* grid units by definition, the function has exactly one caller, and it now
converts unconditionally under a name that states the contract --
`_preset_columns_to_pixels`. The check asserts six conversions rather than a heuristic, and
records why there is deliberately no case for a small pixel position.

Verified against the live server, all three paths:

    graph preset      [0,0] .. [1120,0], px=true on every node
    drag to (5,0)     stays [5.0, 0.0], px=true
    palette at (300,240)  [300.0, 240.0], px=true

and each of those was a path that could produce the jump before. The palette one is the one
that had never been marked.

Three checks now guard it: the conversion is by contract, every route that places a node
states its unit, and the canvas no longer converts at all. The last one is the important one
-- the previous design kept adding client-side machinery, and this asserts that it is gone
rather than trusting that it stays gone.

Also fixed on the way: the helper function was first inserted inside the `App` class, because
the anchor I used sits inside it, which turned it into a method and broke `/api/graph/preset`
with a 500. The restore-then-reapply is why the final version asserts the anchor count and
verifies by import rather than by reading.

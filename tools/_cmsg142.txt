wire the near-infrared albedo to a local vision model, with the brightness estimate as the documented fallback

**What `note.txt` asks for and what the model did instead.**  The note's second mechanism:

    "给场景材质设置近红外反射率，而不是直接把 RGB 转成灰度。植被、织物、皮肤、塑料和涂漆表面的近红外响应可能与可见光观感不同。
     这是普通夜视滤镜最难自然模拟的部分之一。"

**and the model estimated near-IR albedo as `lum ** 0.55`** -- brightness raised to a power, which is the RGB-to-grey
route the note says is the hardest thing to make natural.  `nightvision.IR_ALBEDO` already carried the measured
orderings (**foliage 2.10, skin 1.55, dark clothing 0.28** -- a **7.5x range**) with nothing reading them, because a
visible photograph does not say which material is where.

**A vision-language model does.**  `atsim/codecs/material.py` labels the scene in an NxN grid using
`siglip2-base-patch16-224` -- **the prompts are `IR_ALBEDO`'s own keys**, so the table and the classifier cannot drift
apart -- and `nightvision.albedo_map` turns the labels into a per-pixel albedo normalised about its own mean, so the
*relative* response the table describes is applied without touching the picture's level.

**Measured on the reference photograph** (mode 2, the schema's own settings):

    provenance  siglip2-base-patch16-224: glass 18, metal 17, paint_coloured 9, dark_clothing 9, skin 7, unsure 3, white_fabric 1
    the albedo   min 0.344  max 2.001  mean 1.000   -> 5.81x across the frame
    the model    luma 0.2230  contrast 0.1930
    the estimate luma 0.2390  contrast 0.2004
    the footage  luma 0.2346  contrast 0.2032

**and the honesty that figure demands**: on these two scalars **the estimate is closer** -- contrast 0.2004 against the
footage's 0.2032, where the material model gives 0.1930.  **That is not evidence the material model is wrong**, because
the whole premise is that near-IR albedo is *not* a function of visible brightness; a model that agrees with the
brightness estimate more closely would be reproducing the very correlation it exists to break.  **But it does mean the
material model is not yet shown to be better on this scene, and it is not claimed to be.**  This scene is also the worst
case for it: a plastic case, a painted wall and a floor, whose table values (1.05-1.20) are nearly equal -- the model's
value would show on foliage, skin or dark clothing, and this footage has none.

**The fallback is a supported configuration, not an error path.**  `material.available()` reports whether a checkpoint
can be loaded and never raises; where it cannot, `_attach_ir_albedo` records *why* it estimated
(`nir_label_source = "estimate (no vision model found)"`) and the picture is the brightness estimate, which is exactly
what a user without a model gets.  **Verified in the end-to-end run**: `nv_nir_material = 0` produces the estimate, and
the two panels differ by 0.0160 in luma and 0.0074 in contrast, i.e. a change of appearance rather than of level.

**And every label carries its confidence, so the two sources mix per cell.**  Measured, the model's margin over the
runner-up runs from **0.692 down to 0.030**, so a label at 0.03 is worth nothing and must not be allowed to put
foliage's 2.10 on concrete.  Cells below `nv_nir_margin_floor` (default 0.02) take the estimate instead -- on the
reference frame that is **3 cells of 64**, and the weighting is continuous in the margin rather than a hard switch.

**New parameters**, all in the camera layer with the model's usual provenance comments:

    nv_nir_material      1.0     whether to label materials at all
    nv_nir_grid          8       the NxN lattice
    nv_nir_margin_floor  0.02    below this a cell falls back to the estimate

**and the checkpoint is named by `ATSIM_NIR_MODEL` rather than by a parameter**, because every parameter in this schema
is numeric and a path is not -- and because naming a model is a property of the machine, not of the look being simulated.

**The default path is byte-identical**: with no labelled map, `albedo_map` returns ones and `ir_highlights` multiplies by
one, verified against the previous behaviour (`spread 0.351978` both ways) and by the suite.  **163 checks pass.**

**Two corrections to the previous round, both mine.**  The figure's albedo panel rendered as diagonal streaks in the
first two attempts -- `np.resize` flattens and re-tiles, and the stage caches the map at *full picture size* so the
reduction back to the grid has to be explicit.  **A map that looks wrong while being right is how a correct model gets
rejected**, so it was fixed rather than shipped.  And the figure's own caption for the estimate panel printed `None` for
provenance, because the stage short-circuits before recording a reason when the switch is off -- the caption now says
what it is instead of reading as an absence.

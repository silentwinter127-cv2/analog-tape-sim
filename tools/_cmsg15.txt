normalise the graph to pixels where the graph is built, so the start-up path cannot miss it

Reported: "the nodes start out stacked on top of each other". The start-up graph is constructed
in `App.__init__` as `GRAPH_PRESETS["vhs_consumer"]["build"]()`, which produces grid columns, and
only `graph_load_preset` converted them. So a freshly booted server handed the canvas
`[0,0] [1,0] [2,0] ...` -- one unit apart, which is a single pile of nodes. Loading a preset from
the UI looked right, which is why it only appeared on a fresh start.

Measured before and after on the real graph:

    (0, 0) (1, 0) (2, 0) (3, 0)                  spacing 1
    (0, 0) (224, 0) (448, 0) (672, 0)            spacing 224

**This is the same shape as the bug that made positions ambiguous in the first place.** The rule
existed in one path and not in another, so a graph could be in grid units depending on how it was
created. The conversion has therefore moved onto the graph itself, as
`Graph.normalise_positions()`, and both the preset route and the start-up constructor call it --
so a future path that builds a graph is one call away from being correct rather than one omission
away from being wrong.

The conversion stays unconditional, and that is still the right call: every construction path
starts from a preset entry authored in columns, and a value-based test is impossible because
column 5 and pixel 5 are the same number. The unit comes from the caller, and now the caller is
the graph's own constructor.

Two checks guard it, and they check the paths rather than the arithmetic, because the arithmetic
was never wrong:

  * every graph preset, after normalisation, has its nodes spread out by more than 100 px and
    every node marked as pixels -- a graph left in columns spans 5 px and fails;
  * both server routes that build a graph call the normalisation. The rule living in one path and
    not the other is precisely what produced the overlap.

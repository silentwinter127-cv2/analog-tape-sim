**`note.txt` lists exactly this as a mechanism** -- "加入随曝光和信号强度变化的噪声、暗部读出噪声、固定图样噪声，**以及高亮区域的饱和**"

**so the mechanism is MISSING rather than mistuned**, which is the more serious of the two possibilities and is what the

**2. The illuminator reaches its term and changes nothing.**  `nv_illuminator` set to 0.15, 0.30, 0.50, 0.80, 1.20, 2.00
and 3.00 gives **bit-identical output**, and a probe inside `add_illuminator` shows the value **does arrive** -- 0.15
reaches the function as 0.150, 0.80 as 0.800, 3.00 as 1.000 (clipped at the parameter's own ceiling).  **So this is not
the swallow a value has suffered five times before in this work** -- `chroma_residue`, `accumulate`, `ir_response`,
`ir_albedo`/`ir_depth`, and the player's six parameters all had their values replaced before use.  **Here the value arrives
and the arithmetic makes it inert**, which is a different fault in the same family: the one this file already records for
`tbc_enabled` ("the parameter was read; the arithmetic made it inert").

**The candidates are few and the next step is specific**: `illuminator_field` normalises by its own mean and scales by a
constant, and `add_illuminator` applies the field to the picture -- so either the field is being renormalised downstream,
or the picture's own brightness is standing in for the lamp's response in a way that cancels the scale.  **Printing the
field's statistics and the picture's change across two settings would name it**, which is the same probe method that found
the last five.

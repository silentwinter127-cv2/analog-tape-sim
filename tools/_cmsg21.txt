add the camera's automatic control loops: exposure, white balance, and focus

The note's sixth dimension, and it names the reason it matters: the camera is always making small
automatic mistakes, and that is where a consumer camcorder's character comes from. A handycam has no
operator setting exposure; it has a loop that measures the picture and moves a control, with a time
constant.

**These are the only mechanisms in the model that carry state forward**, because they read the picture:
exposure at frame N depends on what the loop has seen. Everything else added so far is a function of the
frame number, which is what makes it safe to render frames in any order. The renderer pumps frames from
zero and caches each stage per frame, so the loop is walked once per frame in order -- correct by
construction given that discipline, and the invariant is written down where the loops live rather than
assumed.

**Exposure** tracks centre-weighted scene luminance with a dead band, so it does not hunt on grain. A
real metering pattern is not an average, and the consequence is wanted: a bright sky does not drag the
exposure down as far as a flat average would, which is why camcorder footage so often has a blown sky.

**White balance** nulls the scene's average chroma, and that is *the* source of the colour drift that
reads as a 1990s home recording: the loop nulls the lamp, so a room lit by a warm bulb goes neutral over
a second or two and swings back when the camera turns to a window. A static cast cannot drift, which is
the whole argument for a loop rather than a slider.

**Focus** hunts, because it cannot measure focus -- only contrast -- so it steps, watches whether
contrast improved, and reverses when it did not. On a low-contrast scene it never finds a peak and keeps
looking, which is the behaviour the note describes as clear-blurry-search-clear. A fixed defocus cannot
produce that at all.

**Three faults, and they are the same shape.** The first two are one mistake in opposite directions:

  * `self.exposure += loop.update(...)` used the loop's return but *added* it to the current value, so
    the correction compounded -- measured, a scene needing +1.5 stops went 0.06, 0.85, 2.43 and sat at
    the +3.0 limit, leaving the picture at 0.87 against a 0.46 target;
  * `self.exposure = loop.state` used the right value but read it from *before* the step, so the loop
    stepped correctly every frame and its result was never used -- measured, exactly 0.0000 of correction
    on a scene needing +1.5 stops;
  * the loops themselves jumped to their target on the first frame, because `_seeded` bypassed the
    decay. Measured, tau 1.5 s and tau 4.0 s produced bit-identical trajectories, so the time constant
    the docstring promised did not exist.

The form that cannot do either of the first two is `self.exposure = loop.update(...)`, because the step
and the read are one expression. That is what it is now.

**Four assertion faults too**, all in the checks rather than the mechanism, and worth recording because
each one would have hidden a real fault: expected a first-frame jump a correct loop does not make;
demanded an exponential be within 0.35 stops of its asymptote after two time constants; used a source
whose first frame was already at the metering target, so a working loop had nothing to do (0.0082 of
difference, indistinguishable from an inert one); and compared frame 0 with the last frame of a loop
that converges in under a second, so both ends were already corrected.

Measured: exposure error +1.46 stops at 0 s, +0.54 at 1 s, +0.004 at 6 s against a +1.52 target, and
falling monotonically; the time constant orders the adaptation 1.5 s against 4.0 s by a factor of 2.2;
all three loops default off and a loopless camera renders frame-for-frame identically.

94 checks pass, 15 presets render.

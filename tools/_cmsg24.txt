add the dimension panels: environment, device individual, and the keyframe timeline

Seven dimensions had been built into the engine and **none of them was reachable from the interface** --
they could only be set by writing Python. That was the largest usability gap in the project, and the
keyframe timeline in particular is its most distinctive mechanism and had no editor at all.

**Three panels, added without touching what exists.** They mount into the existing left column, load from
a template the server already serves, and reuse `api`/`jsonPost`/`S`/`applyProject`/`toast` from `app.js`
rather than introducing a second state store. So there is one source of truth: `applyProject` calls
`SessionUI.syncFromProject(d)` last, and the panels always show what the server just returned. The CSS is
appended, so no existing rule can break.

**The timeline is a canvas, not a table, because the curve's shape is the content.** An `exp` segment and
a `linear` one can share both endpoints and differ entirely in between, and that difference is exactly what
the user is choosing. The editor draws the curve using the same interpolation the engine uses, so what is
seen is what will be rendered -- the `exp` constant (0.30, reaching about 96% across the segment) appears
in both places with a comment saying so, because two copies of a shape must be checked against each other.
Points are dragged, the empty canvas adds one, and the push is throttled to the pointer release: sending a
request per pixel would make the drag stutter.

**The wiring was the hard part, and the first two attempts to verify it were wrong.** `App.renderer_for`
built renderers from `project.resolved_params()` alone, so the environment and the keyframes **never
reached the renderer**: editing a timeline in the interface would have changed nothing on screen while
every file, field and route looked correct. Both of its paths now call `set_time_varying`, because a cached
renderer invalidated with new parameters still holds the old timeline.

**A real bug found by driving the API rather than by reading it.** `Project.unit_report` reported
`DeviceUnit(identity="probe")` -- a hardcoded string -- so every serial number produced the identical
table of deviations. Measured: "Panasonic NV-GS78 A39482", "Panasonic NV-GS78 99999" and "JVC GR-AX7 00001"
all gave `head_wear=0.361`. The method's own docstring says why that is wrong: a realism claim about a
specific unit is only checkable if its numbers can be read out. The existing device-DNA check did not catch
it because it exercises `resolved_params()`, which was correct -- `unit_report()` is a second, independent
path that duplicated the same computation, and the duplicate was the broken one. Both now share one
`_unit()` helper, so they cannot disagree again. This is the project's recurring lesson in a new form: not
"the instrument measured the wrong thing" but "the instrument measured a different function than the one
being rendered".

**Two demonstration presets, because everything defaults to off.** An unrequested dimension must not move
an existing preset, so a user opening the tool would see none of the seven. `cold_start_handheld` switches
them on together -- a cold camera whose auto-exposure is still settling, held in a hand, recorded on a deck
whose capacitors are going -- and `warm_archival` is the same machine warm and still, as a control. Presets
now carry `environment` and `timeline`, and **clear both when they do not mention them**: inheriting the
previous preset's timeline would make the picture depend on the order presets were clicked, which is the
fault `apply_preset`'s own docstring describes.

The profile-keys check caught `tape.head_wear` in both new presets -- head wear is the machine's, not the
medium's, and the schema had it on the player layer. A preset naming a parameter that does not exist is
silently ignored at render time, so it would have looked slightly wrong rather than failing.

fix multi-line subtitles: every line was drawn at the same row

`parse_lines` split a string on newlines and never advanced the row:

    parse_lines("LINE1\nLINE2") -> [("LINE1", row=0), ("LINE2", row=0)]

so both lines landed at `margin_y + 0 * cell`, one on top of the other, and the frame showed a single pile of
overlapping glyphs. It reads as a font or rasterising fault, and the glyph count, the missing-character report
and the mean-luma change were all correct while it was happening -- which is why four checks passed and the
subtitle still looked wrong.

**Every test up to that point used one line**: `"REC 00:12:34"`, `"TITLE 标题"`, `"婚礼"`. A one-line case
cannot reveal a row that never increments, and multi-line input is the first thing a person types. The new
check uses two lines and asserts *separate ink bands* rather than a glyph count, because the count was never
the thing that was wrong.

An explicit `row` in a dict is now an offset from the line's own position rather than a replacement for it, so
a caller can place one line and still let the rest stack below it instead of having them all share that row.

**This turn's fault was the same shape as the last one.** The subtitle did not appear because the server on
8941 was running old Python -- static files are read from disk per request and the process is not, so the
interface showed a new panel whose engine had no `overlay` layer at all, and `resolve_all` dropped the whole
layer before it reached the stage. Then, with the server current, the text appeared but its lines overlapped.
Both were found by exporting a frame and looking at it, after the numbers had said everything was fine --
which is the third time in this feature that a measurement was satisfied by something other than the thing it
named.

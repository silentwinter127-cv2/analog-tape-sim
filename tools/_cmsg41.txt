add draggable splitters and Blender-like workspaces

**Blender's workspaces are not extra features.** They are the same editors, arranged and shown differently,
switched from a row of tabs, each remembering its own arrangement. That is what this is, and it fits here because
the interface has two populations at once: someone building a chain wants the device catalogue and the graph,
and someone grading an artefact wants the picture as large as possible with the parameters beside it. Both use
the same panels.

**Splitters.** The two panel edges drag, clamped, restored with a double-click, and persisted per workspace. The
widths live in two CSS variables on the grid, so the layout stays declarative and no element needs an inline
width.

**Workspaces.** 组合 / 建模 / 调参 / 观看 / 时间线, switched by tab or by Ctrl+Alt+1..5, plus 重置布局. **A
workspace changes only which editors are visible -- never project state.** That is the property that makes one
safe to click, and it is the thing to preserve if this grows.

**Verified live, not by reading, because the headless browser was available.** Chrome is on this machine, so the
page was driven over the DevTools protocol rather than inspected:

    drag the left splitter    270 -> 390 px, and the stage 864 -> 744
    workspace 观看              the stage takes the full 1484 px, no panels, no residue
    workspace 建模             left panel only: stage 270 -> 1484
    workspace 调参             right panel only: stage 0 -> 1144
    persistence                {"active":"layout","widths":{"layout":{"left":390}}}

**Two faults found by measuring rather than by looking, and both were valid CSS that lays out wrongly.**

  * **the splitters were grid items.** `grid-template-columns` named a five-pixel `lspl` track, and a named track
    does not collapse while the stage is explicitly placed beyond it: the workspace hiding both panels gave
    `stageLeft: 5` instead of `0`. Making the splitter zero-width did not help, because the *track* was the
    problem. They are absolute overlays now, so the grid has three columns and a hidden panel's track collapses
    on its own -- which also removed the need for a special case;
  * **the collapsed-splitter rule lost a specificity tie.** `display: block !important` was written to keep the
    element in the grid with no width, and the measured grid was `0px 5px 1474px 5px 0px` -- the splitters were
    still holding their tracks. `!important` does not win a tie against a later rule.

**And the check I wrote for it failed on three innocent components before it was right.** It looked for any
hardcoded `grid-template-columns` and flagged the timeline and the parameter rows, which legitimately size
themselves. A check that fails on unrelated things carries no more information than one that cannot fail, and
this project has now produced both. It is scoped to the `main` rules, which is where the fault would be.

derive the overlay's font list from the registry, and roll back the highlight work

**The fonts were unreachable, and it is the fourteenth occurrence of this project's most common defect.** The
registry grew from three fonts to fifteen and the panel builds its dropdown from the registry, but the overlay
stage still held its own copy:

    FONTS = ("osd", "lyusung", "apos")
    key = self.FONTS[int(np.clip(round(self.font_kind), 0, len(self.FONTS) - 1))]

so every index above 2 was clamped to `lyusung`. Measured over the API: **fourteen distinct font indices were
posted and the server drew `lyusung` every time.** The interface showed fourteen fonts and all of them drew the
same one -- a list agreeing with itself and not with the engine.

It is derived from `font_catalogue()` now, which is the registry's own view and filters entries whose file is
missing, so the panel and the engine cannot disagree about either the order or the availability. Verified index
for index: fourteen and fourteen, identical.

**The highlight work is rolled back, and that is the honest outcome.** The chain's shoulder was asymptotic --

    comp = knee + (1 - knee) * (1 - exp(-(lin - knee) / (1 - knee)))

-- so it approached 1.0 and never arrived, and measured, a lamp at twice the reference white came out at 0.786:
**no pixel in any picture could be pure white.** That is a real defect and it is why the highlights in the user's
reference cannot be reproduced. I replaced it with a saturating curve whose white point follows `dynamic_range`,
and that part worked: the camera's own output reached 1.000 over 432 pixels.

But holding the saturation through the rest of the camera broke the auto-white-balance check -- the clip's colour
cast stopped being reduced at all, 1.1033 at frame 0 against 1.1072 at frame 59 -- and the hold is a hard clamp on
exactly the pixels the balance loop needs to move. Moving it before the colour science did not fix that, clearing
the mask per frame did not fix it, and by then I had made fifteen edits to one file and made it worse rather than
better. **The suite is green again at 143 checks, and the highlight chain is unchanged from where it started.**

What is established for the next attempt, so it does not have to be rediscovered:

  * the shoulder **must** saturate; the white point following `dynamic_range` is `2 ** ((dr - 8) / 8)`;
  * `_sharpen` takes the peak from 1.191 to 1.116 by averaging a saturated core down, so any hold has to survive
    it -- instrumenting `apply` method by method is what showed that, after reading the file had been wrong twice;
  * and **a hold implemented as `np.maximum(rgb, 1.0)` conflicts with the AE and AWB loops**, which is a design
    question rather than a line of code: saturation belongs at the imager, so the loops should act on a value that
    is allowed to exceed white rather than on one clamped to it.

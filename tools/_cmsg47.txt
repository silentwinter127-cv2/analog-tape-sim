record the OSD slot's whole-frame effect, and what stands in the way of fixing it

**The user reported this twice and I measured the wrong thing both times.** With the overlay *disabled* the two
slots produce byte-identical frames, so I concluded the slot was innocent -- but the observation is about the
picture they are actually looking at, which has the overlay **on**. Measured properly this time:

    inside the text's region    mean |diff| 0.04424
    OUTSIDE it                  mean |diff| 0.03244     <- the whole picture
    pixels differing by >2%     285486 of 406272 (70.3%)
    maximum difference          0.96
    with the text off           outside |diff| 0.00000, max 0.00000

So switching the generator to the titler position changes 70% of the frame by up to 96% of its range, from a
feature whose job is to add a caption. **That is the report, and it is real.**

**The mechanism.** At `at=1` the text is written before the recorder, so the frame must carry the text in the
signal the downstream stages rebuild from -- that is what the overlay's YIQ round trip and composite rebuild were
added for, and without them the display discarded the text entirely. But the round trip is applied to the **whole
frame**, and the display then rebuilds the whole picture from the re-encoded signal.

**Two candidate fixes, and both are blocked, which is the useful part of this record.**

*Making the overlay re-encode only the text's pixels* is the obvious one. It is not a small change: the stage
publishes `rgb`, `signal` and `composite` and would have to blend into all three under a mask.

*Removing the display's reconstruction* (`rgb = buf.rgb if sig is None else sig.to_rgb()`) half worked -- the
outside-the-text difference fell from 0.032 to 0.0066 and the affected pixels from 70% to 9.6% -- and it **broke
the medium**: with `wear 0.9` the damage contributed 0.00001 to the output, i.e. the tape's damage was lost. It is
reverted.

**And probing that second one turned up something else.** The display's own comment says the reconstruction exists
so that "with the display stage disabled the frame handed to the user is this image", because returning a
pass-through RGB would "silently discard every bandwidth, crosstalk and time-base change upstream". Measured:

    format layer, bandwidth 1.2 vs 4.0    display on 0.05636   display off 0.05530   reaches the picture
    tape layer,   wear 0.9 vs tape off    display on 0.00001   display off 0.00002   **no contribution at all**

So the format layer's damage does reach `rgb` and the tape's does not -- and the tape's does not even when the
display is enabled, which means **`tape.wear` contributes nothing to the picture by either route**. That is a
separate defect from the OSD slot, and it is not yet diagnosed.

**What to do next, deliberately not now.** The two fixes above are patches on a chain whose invariant is not
stated. The invariant is:

    a stage that changes the picture changes `rgb`, `signal` and `composite` together;
    a stage that changes only the signal changes both `rgb` and the signal.

If every stage obeyed it, the display would need no reconstruction and the overlay could re-encode freely. The
work is to establish that invariant and let the checks hold it -- not to add a fourth special case beside the
three that are already there. The user has asked for the highlight round next; this record is so that the slot
work can start from the invariant rather than from another measurement.

The repository is at 143 checks, green.
